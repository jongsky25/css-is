# Audit warning investigation — November 1, 2026

User requested the deferred audit investigation and reported backups fixed.
Backup remediation and automatic alerting are outside this change.

## Read-only evidence

Inspected existing private-bucket snapshot `css_is_20261101_083807_auto.db`
with SQLite `mode=ro` in a mode-0700 temporary directory. The application was
never started against it. The snapshot contained 10,678 audit rows and exactly
the same three failures recorded in the earlier investigation:

- **8949:** previous link correctly references 8948. Stored target ID is text
  `"0"`. Recomputing the hash with numeric zero instead of stored text exactly
  matches the original hash. `_audit_hash` treats numeric zero as empty, while
  `audit` previously converted the ID to text only for insertion. This reproduces
  the content mismatch without changing any record.
- **9406:** content hash validates with its own stored parent, but that parent
  is 9404 rather than 9405.
- **9452:** content hash validates with its own stored parent, but that parent
  is 9450 rather than 9451.

The latter two are forks consistent with the writer reading the latest hash
before obtaining SQLite's writer reservation. Snapshot evidence establishes
the parent relationships, not the precise historical request interleaving.
No evidence here establishes malicious alteration or independently authenticates
the original business records. No record prose, identities or hashes are published.
The downloaded snapshot and temporary SDK staging directory were removed.

## Candidate fix and remaining warning

`storage.audit` now converts target IDs before hashing and obtains a writer
reservation with `BEGIN IMMEDIATE` before reading the tail when no transaction
is active. Caller-owned write transactions and `commit=False` retain their
existing commit/rollback ownership. SQLite's existing busy timeout still applies;
an existing deferred read transaction that cannot upgrade fails rather than
silently appending a fork. No historical hashes or verifier rules change.

New regression coverage exercises numeric-zero IDs, simultaneous independent
writers, caller rollback/commit and continued detection of old corruption.

This prevents the reproduced write defects after deployment. It does **not**
clear the live historical warning. Rehashing old records would conceal the
original discrepancies. A separately designed, explicitly approved historical
incident acknowledgment/checkpoint would be needed to distinguish an accepted
historical incident from new failures without discarding this evidence.
No live database mutation, restart, merge or production deployment is included.
